# Roadmap

Три волны. Статус на 2026-11-05.

## Волна 1 — ядро (реализована)

Библиотечное ядро: генерация фингерпринтов, шифрованное хранилище, прокси,
лаунчер со спуф-слоем. Управление — программное (UI/CLI/API добавлены в волне 2).

| Модуль | Путь | Зона ответственности | Статус |
|---|---|---|---|
| mirage-core | `crates/mirage-core` | структуры Fingerprint/Profile, генератор из seed, валидатор консистентности, загрузка fp-db | реализовано |
| fp-db | `fp-db/` | базы реальных значений: GPU, шрифты, экраны, локали | реализовано |
| mirage-vault | `crates/mirage-vault` | шифрованное хранилище (Argon2id + AES-256-GCM), `.mprof` | реализовано |
| mirage-proxy | `crates/mirage-proxy` | SOCKS5 (RFC 1928/1929), HTTP-CONNECT, проверка exit-IP | реализовано |
| mirage-launcher | `crates/mirage-launcher` | поиск Chrome, сборка аргументов, spawn, CDP-клиент, инъекция спуф-слоя | реализовано |
| inject | `inject/` | JS-спуф слой (10 модулей, порядок склейки — CONTRACT.md) | реализовано |
| patches | `patches/` | нативные патчи Chromium (шрифты, чтение canvas) | реализовано |
| CI, smoke | `scripts/`, `.github/` | CI и smoke-скрипты | реализовано |

Контракт данных и модулей волны 1 — [CONTRACT.md](CONTRACT.md), обязателен к
исполнению буква-в-букву.

Критерии готовности волны 1 (все три обязательны):

1. `cargo test --workspace` зелёный во всех крейтах.
2. Запуск профиля через launcher: профиль, созданный в vault, стартует в Chrome
   с прокси, спуф-слой применён до скриптов страницы.
3. whoer.net не видит противоречий в подменённых полях (язык, таймзона, IP,
   WebRTC) — методика проверки в [DETECTION.md](DETECTION.md).

## Волна 2 — продукт (реализована)

| Модуль | Зона ответственности |
|---|---|
| Локальный REST API | совместимость с AdsPower Local API — миграция скриптов без переписывания |
| UI | Tauri |
| CLI | управление профилями из терминала |
| Cookie | импорт/экспорт cookie |
| Импорт профилей | из Dolphin Anty, AdsPower, GoLogin |
| Синхронизация | self-hosted синк команд, первая версия |
| Python SDK | клиент локального API |
| Упаковка | инсталлятор, релизы |
| E2E | e2e-тесты сценариев волны 2 |

Критерии готовности волны 2:

1. Создание профиля через UI.
2. Создание профиля через локальный API.
3. Импорт профиля из AdsPower: фингерпринт и прокси переносятся, профиль
   проходит валидацию консистентности.

## Волна 3 — команда и автоматизация (план)

- **Командная синхронизация с ролями:** полный командный цикл поверх
  sync-сервера волны 2 (сервер с API-ключами и ролями `admin`/`member` уже
  есть) — клиентская интеграция, управление ключами и ролями.
- **Мобильные профили:** мобильные фингерпринты.
- **Автообновление калибровки Chrome:** лаунчер читает реальную версию
  `chrome.exe` и скармливает её генератору автоматически (см. открытый
  вопрос 3).

Критерий готовности волны 3: командная синхронизация работает между двумя
машинами через свой сервер.

## Открытые вопросы

1. **Прокси с авторизацией из коробки.** Chromium не принимает логин/пароль в
   `--proxy-server`. Варианты: bundled-расширение (перехват `onAuthRequired`)
   или локальный конвертер прокси. Схема Profile уже хранит `username`/`password`
   — нужен только канал применения.
2. **Мобильные фингерпринты.** Кроме UA и экрана нужны touch-события, сенсоры,
   поведение скролла. Оценить объём после волны 2.
3. **Обновление Chrome-версии в данных.** CONTRACT и fp-db калиброваны под
   Chrome 156 (`CHROME_MAJOR`, `CHROME_FULL`, UA Reduction с заморозкой минорных
   версий в `.0.0`). Нужна процедура обновления: UA-шаблоны, brands,
   clientHints, пересборка баз, регресс-тесты. План волны 3: лаунчер читает
   реальную версию из `chrome.exe` и скармливает её генератору автоматически.
   Открыто: как часто обновляться и
   насколько отставать от стабильного Chrome.
